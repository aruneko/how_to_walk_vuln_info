# Ubuntu 演習：解答と解説

> 演習が終わってから読んでください。USN は 2026年10月21日時点、KEV は 2026年10月16日版、NVD は 2026年10月20日時点の情報にもとづいています。

## 問1：deb のバージョン比較

| # | 比べるもの | 新しいほう | 理由 |
|---|---|---|---|
| 1 | `3.0.13-0ubuntu3.15` と `3.0.13-0ubuntu3.16` | **`3.0.13-0ubuntu3.16`** | 上流のバージョン（3.0.13）は同じ。リビジョンの最後の数字 15 と 16 を比べる |
| 2 | `6.17.0-29.29~24.04.1` と `6.17.0-29.29` | **`6.17.0-29.29`** | `~` は「何もない」よりも小さいので、`~24.04.1` が付いているほうが古い |
| 3 | `1:9.6p1-3ubuntu13.18` と `9.7p1-1` | **`1:9.6p1-3ubuntu13.18`** | 左はエポックが 1、右はエポックが省略されているので 0。エポックが最優先で比べられる |
| 4 | `1.1.1f-1ubuntu2.24` と `1.1.1f-1ubuntu2.24+esm6` | **`1.1.1f-1ubuntu2.24+esm6`** | `+esm6` が付いているほうが大きい |

2 の `~24.04.1` は、新しいリリース向けのパッケージを古いリリースに持ち込んだ（バックポートした）ときによく使われる書き方です。`~` を付けることで「本家のリリースのものより少しだけ古い」ことを表しています。

## 問2：OpenSSL は影響を受けるか

### 1. NVD の CPE で判定すると

NVD の CVE-2026-54874 の CPE は、`openssl:openssl` の「3.0.0 以上 **3.0.22 未満**」などが影響を受けるとしています。web01 の OpenSSL は上流のバージョンが **3.0.13** なので、この範囲に入り、**影響を受ける**と判定されます。

### 2. USN にもとづくと

CVE-2026-54874 は **USN-8678-1** で修正されています（`upstream` に `UBUNTU-CVE-2026-54874` がある）。修正バージョンは `3.0.13-0ubuntu3.15` で、web01 の `libssl3t64` と `openssl` はちょうど `3.0.13-0ubuntu3.15` なので、**修正済み**です。

結論が違うのは、Ubuntu が OpenSSL の修正を **3.0.13 にバックポート**しているからです。Ubuntu 24.04 の OpenSSL は、上流のバージョンは 3.0.13 のまま、リビジョン（`-0ubuntu3.15` の部分）を上げることで修正を取り込んでいます。NVD の CPE は上流のバージョンだけで判定するため、この修正を見分けられず、**偽陽性**になります。

### 3. ソースパッケージとバイナリパッケージ

`openssl` は**ソースパッケージ**の名前で、そこから複数の**バイナリパッケージ**が作られます。USN-8847-1 の `ecosystem_specific.binaries` を見ると、`openssl` ソースパッケージからは次の 2 つが作られています。

| バイナリパッケージ | 役割 |
|---|---|
| `libssl3t64` | OpenSSL の**ライブラリ**。nginx や openssh などが使っている |
| `openssl` | `openssl` **コマンド** |

脆弱性の多くはライブラリの側にあるので、**両方とも**更新する必要があります。特に `libssl3t64` を見落とすと、`openssl` コマンドだけ更新しても nginx は脆弱なままになります。

> **補足**：ライブラリを更新したあとは、そのライブラリを使っているプログラム（nginx など）を**再起動**しないと、古いライブラリがメモリに読み込まれたままになります。Ubuntu では `needrestart` というツールが、再起動が必要なサービスを教えてくれます。

カーネルは、`linux-image-6.8.0-110-generic` と `linux-image-6.8.0-138-generic` の 2 つがインストールされています。パッケージとしては、新しいほう（6.8.0-138.138）で判定します。

### 2. 未適用の CVE の数と、必要な作業

- 未適用の USN は **5 件**、含まれる CVE は合わせて **1,297 件**（11 ＋ 3 ＋ 1 ＋ 232 ＋ 1,050。重複はない）
- 更新が必要なソースパッケージは **4 つ**（linux、openssl、openssh、nginx）

CVE が 1,297 件あると聞くと途方に暮れそうですが、**やるべき作業は「`apt upgrade` して、サービスを再起動し、サーバーを再起動する」だけ**です。第7章で見た「RHSA・USN と CVE の多対多」の関係が、ここに表れています。

### 3. 束の中の KEV

| CVE | KEV に追加された日 | 含んでいる USN |
|---|---|---|
| **CVE-2026-53266** | 2026-09-18 | USN-8903-1（linux、232 件の 1 つ） |
| **CVE-2026-53362** | 2026-08-27 | USN-8917-1（linux、1,050 件の 1 つ） |

どちらの USN も、見出しは「linux vulnerabilities」というだけで、KEV に載った脆弱性が含まれているとは書かれていません。**束の中身を KEV と突き合わせて初めて分かる**ことです。

また、CVE-2026-53362 は 8 月 27 日に KEV に追加されましたが、Ubuntu 24.04 の修正（USN-8917-1）が出たのは 10 月 13 日でした。**KEV に載ってから修正が出るまでに 1 か月半以上かかる**こともある、ということです。

### 4. BOD 26-04 の修正期限

| CVE | 公開状態 | KEV | 自動化可能性 | 技術的影響 | 修正期限 |
|---|---|---|---|---|---|
| CVE-2026-53266 | はい | はい | no | total | **3 日 ＋ フォレンジックトリアージ**（3 行目） |
| CVE-2026-53362 | はい | はい | no | total | **3 日 ＋ フォレンジックトリアージ**（3 行目） |

どちらも、ローカルから権限を昇格する脆弱性（CVSS の攻撃元区分が `AV:L`）です。「インターネットから直接攻撃されるわけではない」と考えがちですが、BOD 26-04 では**資産が公開されているか**で判断します。公開サーバーでは、Web アプリケーションの脆弱性などで一度入り込まれると、そこから管理者権限を奪われる足がかりになるためです。

したがって、**カーネルの更新（USN-8917-1 まで）が最優先**で、OpenSSL・OpenSSH・nginx も同じ `apt upgrade` でまとめて更新します。

## 問4：本当に直っているか

### 1. CVE-2026-31431 の影響を本当に受けていないか

**受けています。** `uname -r` は `6.8.0-110-generic` で、`uptime` は 183 日です。つまり web01 は、**4 月に起動したときのカーネル 6.8.0-110.110 で今も動いています**。

9 月 1 日の `apt upgrade` で修正版のカーネル（6.8.0-138.138）は**インストールされました**が、**再起動していない**ので、まだ使われていません。USN-8278-1 の修正バージョン 6.8.0-117.117 よりも古いカーネルが動いているので、CVE-2026-31431 は**修正されていません**。

| 判定の根拠 | 判定 |
|---|---|
| `dpkg -l`（インストールされているパッケージ） | 修正済み |
| `uname -r`（実際に動いているカーネル） | **未修正** |

カーネルは、**再起動しないと修正が反映されない**数少ないパッケージの 1 つです（ライブパッチを使っている場合を除く）。パッケージのバージョンだけを見るスキャナでは、この状態を見落とすことがあります。

さらに、CVE-2026-31431 は **5 月 1 日に KEV に追加**されています。web01 は、実際に悪用されている脆弱性を抱えたまま、**5 か月以上インターネットに公開されていた**ことになります。

### 2. 次にやるべきこと（解答例）

1. **フォレンジックトリアージ（侵害されていないかの確認）**：KEV に載っていて、技術的影響が total の脆弱性が、長期間公開サーバーに残っていた。BOD 26-04 の考え方では、修正だけでなく、**すでに侵入されていないか**の確認が必要。修正のための再起動で痕跡が消えることがあるので、**ログなどの証拠を先に保全**する
2. **`apt upgrade` で、すべてのパッケージを最新にする**：カーネルは USN-8917-1 の 6.8.0-147.147 以降、OpenSSL・OpenSSH・nginx も最新版にする
3. **再起動する**：新しいカーネルで起動し直す。再起動後に `uname -r` で、`6.8.0-147-generic` 以降になったことを確かめる
4. **再発を防ぐ**：`/var/run/reboot-required` を監視する、定期的な再起動の時間を決める、自動更新（`unattended-upgrades`）やライブパッチ（Ubuntu Pro の Livepatch）を検討する

## 問5（発展）：サポートが切れたリリース

### 1. old01 の OpenSSL は修正済みか

USN-8847-2 の Ubuntu 20.04 向けの修正バージョンは `1.1.1f-1ubuntu2.24+esm6` です。old01 の `1.1.1f-1ubuntu2.24` は、問1-4 で見たとおりこれより古いので、**修正されていません**。

### 2. 何が必要か

`ecosystem` は `Ubuntu:Pro:20.04:LTS` になっています。Ubuntu 20.04 LTS は 2025年5月に**標準サポートが終了**しており、それ以降の修正は **Ubuntu Pro**（ESM：Expanded Security Maintenance）の契約をしたマシンにしか配布されません。`+esm6` の `esm` はそれを表しています。

old01 は `pro status` で「Ubuntu Pro に登録されていない」と表示されているので、**`apt upgrade` を実行してもこの修正は届きません**。対応は次のどちらかです。

- **Ubuntu Pro に登録する**（個人利用なら一定台数まで無料。組織での利用は契約が必要）
- **サポート中のリリース（24.04 LTS など）に移行する**

ディストリビューションの**サポート期間**も、脆弱性対応の一部だということです。「`apt upgrade` していれば安全」なのは、サポート期間中のリリースに限られます。
