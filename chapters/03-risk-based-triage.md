# 3. リスクベースの脆弱性トリアージ

> 目安時間: 10分

## この章のねらい

## 3.1 なぜ CVSS の大小だけでは足りないのか

第1章で見たように、CVE は 2025年と2026年（10月20日まで）だけで **13 万件以上** 公開されています。このすべてに同じ熱量で対応することはできません。そこで「どれから対応するか」を決める作業、つまり**トリアージ**が必要になります。

これまでよく使われてきたのは「CVSS 基本スコアが 7.0 以上（High 以上）なら優先する」というルールです。しかし、第2章で見たとおり、CVSS 基本スコアは「**最悪の場合の深刻度**」を表すもので、**リスク**を表すものではありません。

リスクは、おおまかに次のように考えられます。

```
リスク ＝ 起こりやすさ（実際に悪用されるか、攻撃しやすいか）
        × 影響（乗っ取られたら何が起きるか、その資産はどれだけ大事か）
```

CVSS 基本スコアには、次の観点が含まれていません。

| 観点 | 例 |
|---|---|
| **実際に悪用されているか** | 攻撃コードが出回り、すでに攻撃に使われている |
| **攻撃を自動化できるか** | インターネット全体を機械的にスキャンして攻撃できる（ワームのように広がりうる） |
| **自分たちの環境でどう使われているか** | インターネットに公開されているのか、社内ネットワークの奥にあるのか |
| **その資産がどれだけ重要か** | 業務の中核を担うサーバーなのか、検証用の端末なのか |

実際に悪用が確認される脆弱性は、全体のごく一部です。後で紹介する CISA KEV に掲載されている CVE は 1,748 件で、リジェクトされたものを除きこれまでに公開された CVE 約 39 万件の **0.5% 未満** にすぎません。「CVSS が高いもの」を全部対応しようとすると、悪用されない大量の脆弱性に手を取られ、本当に危ないものへの対応が遅れてしまいます。

> **ポイント**：リスクベースのトリアージとは、「深刻度が高い順」ではなく「**実際に被害につながりやすい順**」に対応することです。この章では、そのための判断材料を提供する 4 つの仕組みを見ていきます。

## 3.2 CVSS v4.0 の脅威評価基準

### 何を表すのか

第2章で紹介したように、CVSS v4.0 の**脅威評価基準（Threat Metrics）**は、**攻撃の成熟度（E: Exploit Maturity）**の 1 項目だけで構成されています。

| 値 | 意味 |
|---|---|
| **A**（Attacked） | 実際の攻撃が報告されている、または攻撃を簡単に行えるツールが出回っている |
| **P**（POC） | 概念実証（PoC）コードが公開されているが、実際の攻撃は報告されていない |
| **U**（Unreported） | PoC も攻撃も報告されていない |
| **X**（Not Defined） | 評価していない。**A（攻撃あり）と同じ扱い**になる |

基本評価基準と脅威評価基準を組み合わせたスコアは **CVSS-BT** と呼ばれます。E を指定すると、スコアは次のように変わります。

| ベクトル（基本評価基準は共通） | E の値 | スコア |
|---|---|---|
| `AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N` | 指定なし／A | 9.3（Critical） |
| 〃 | P | 8.9（High） |
| 〃 | U | 8.1（High） |

### 誰が値を入れるのか

ここで注意が必要なのは、**攻撃の状況は時間とともに変わる**という点です。CVE の公開時点では攻撃が報告されていなくても、数日後に攻撃コードが出回ることはよくあります。そのため、脅威評価基準は CVE を公開した CNA ではなく、**脆弱性情報を使う側が、最新の脅威情報をもとに埋める**ことが想定されています。

しかし、CVE レコードで CNA が付けた CVSS v4.0 を見ると、E が指定されているものがわずかながら存在しています。こうした場合には、付けた当時から状況が変わっている可能性が高いため、脅威評価基準を自分で差し替え直して評価し直す必要があります。

| CNA が付けた CVSS v4.0（2025〜2026年公開の CVE） | 件数 | 割合 |
|---|---:|---:|
| E を指定していない（項目なし、または X） | 38,145 | 98.1% |
| U（報告なし） | 457 | 1.2% |
| P（PoC あり） | 245 | 0.6% |
| A（攻撃あり） | 41 | 0.1% |

> **注意**：CVE レコードに書かれた CVSS v4.0 のスコアは、ほとんどが「攻撃あり」を前提とした**最悪ケースの値**です。脅威評価基準を活かすには、次に紹介する KEV などの情報を使って、自分たちで E を埋める必要があります。

## 3.3 CISA KEV — 実際に悪用された脆弱性のカタログ

### KEV とは

**KEV（Known Exploited Vulnerabilities）カタログ**は、米国 CISA が公開している「**実際に悪用されたことが確認された脆弱性**」の一覧です。2021年11月、米国の連邦政府機関に対応を義務付ける指令 BOD 22-01 とともに始まりました。誰でも Web ページや JSON / CSV 形式で入手できます。

CISA は、次の 3 つの条件をすべて満たす脆弱性を KEV に掲載します。

1. **CVE ID が割り当てられている**
2. **実際に悪用されたという信頼できる証拠がある**（PoC が公開されているだけでは掲載されない）
3. **明確な対処方法がある**（修正パッチの適用など）

### 掲載されている情報

KEV の各エントリには、次のような情報が含まれます。

| 項目 | 内容 |
|---|---|
| `cveID` / `vendorProject` / `product` | 対象の CVE と製品 |
| `dateAdded` | KEV に追加された日 |
| `requiredAction` | 求められる対応（パッチ適用、利用停止など） |
| `dueDate` | 米国の連邦政府機関に課される対応期限 |
| `knownRansomwareCampaignUse` | ランサムウェア攻撃での利用が確認されているか（`Known` / `Unknown`） |
| `forensicTriage` | 侵害されていないかの調査（フォレンジックトリアージ）が求められるか。BOD 26-04 に合わせて追加された項目 |

2026年10月16日時点の KEV（バージョン 2026.10.16）の状況は次のとおりです。

| 追加された年 | 件数 |
|---|---:|
| 2021 | 311 |
| 2022 | 555 |
| 2023 | 187 |
| 2024 | 186 |
| 2025 | 245 |
| 2026（10月16日まで） | 264 |
| **合計** | **1,748** |

2021〜2022年が多いのは、カタログ開始時に過去の脆弱性がまとめて登録されたためです。全体の約 2 割にあたる 361 件は、ランサムウェア攻撃での利用が確認されています（`Known`）。

### KEV の使い方と限界

KEV は「**少なくともこれは今すぐ対応すべき**」という最低ラインを示すリストとして非常に有用です。多くの脆弱性スキャナや管理ツールも、KEV に載っているかどうかを表示しています。

一方で、次のような限界もあります。

- **網羅的ではない**：CISA が証拠を確認できたものだけが載る。KEV に載っていないからといって、悪用されていないとは限らない
- **掲載までに時間差がある**：悪用が始まってから掲載されるまでに、数日〜数か月かかることがある
- **米国の連邦政府の視点**：連邦政府機関で使われる製品が中心になりやすい

## 3.4 SSVC — スコアではなく「判断」を出す仕組み

### SSVC とは

**SSVC（Stakeholder-Specific Vulnerability Categorization）**は、米国カーネギーメロン大学のソフトウェア工学研究所（SEI）の CERT/CC が 2019年に提案した、脆弱性対応の優先順位づけの手法です。

CVSS との最大の違いは、**数値のスコアを出さず、「次に何をするか」という判断を直接出す**ことです。いくつかの質問（判断ポイント）に順番に答えていく**決定木**の形をとります。また、名前のとおり「**立場（Stakeholder）ごとに**」異なる決定木を使うことが想定されています。たとえば、パッチを当てる側（利用者）と、パッチを作る側（ベンダー）では、判断に必要な情報が異なるためです。

### CISA 版 SSVC の判断ポイント

CISA は利用者（パッチを当てる側）向けに、次の 5 つの判断ポイントを使う決定木を公開しています。

| 判断ポイント | 値 | 誰が答えるか |
|---|---|---|
| **悪用状況（Exploitation）** | `none`（なし）／`poc`（PoC あり）／`active`（実際に悪用） | CISA などが提供 |
| **自動化可能性（Automatable）** | `yes`／`no`：攻撃の偵察・侵入・実行の手順をすべて自動化できるか | CISA などが提供 |
| **技術的影響（Technical Impact）** | `partial`（部分的な制御）／`total`（完全な制御） | CISA などが提供 |
| **ミッションにおける重要度（Mission Prevalence）** | `minimal`／`support`／`essential`：その製品が組織の業務にどれだけ欠かせないか | **利用者自身** |
| **公共の福祉への影響（Public Well-being Impact）** | `minimal`／`material`／`irreversible`：人命や社会への影響の大きさ | **利用者自身** |

### 判断の結果

決定木をたどると、次の 4 つのどれかが結論として出てきます。

| 結論 | 意味 |
|---|---|
| **Track** | 現時点で特別な対応は不要。通常の更新サイクルで対応する |
| **Track\*** | 注意して経過を見守る。状況が変わったら再評価する |
| **Attend** | 組織の管理職に報告し、通常より早く対応する |
| **Act** | 経営層が関与し、できるだけ早く（最優先で）対応する |

### 実際のデータ

CISA は Vulnrichment（第1章で紹介した ADP）を通じて、CVE レコードに SSVC のうち最初の 3 つの判断ポイントを書き込んでいます。2025〜2026年に公開された CVE のうち **92%（120,641 件）** に SSVC の値が付いています。その内訳を見てみましょう。

| 判断ポイント | 値 | 件数 | 割合 |
|---|---|---:|---:|
| 悪用状況 | `active` | 384 | 0.3% |
| | `poc` | 29,064 | 24.1% |
| | `none` | 91,193 | 75.6% |
| 自動化可能性 | `yes` | 30,275 | 25.1% |
| 技術的影響 | `total` | 42,130 | 34.9% |

実際に悪用されている（`active`）脆弱性はわずか 0.3% です。SSVC の値を使うだけでも、膨大な CVE の中から優先すべきものをかなり絞り込めることが分かります。

> **ポイント**：SSVC の後半 2 つの判断ポイント（業務上の重要度、公共の福祉への影響）は、**利用者にしか答えられません**。脆弱性情報の提供者が出せるのは判断材料までで、最終的な判断には「自分たちの環境を知っていること」が欠かせません。

## 3.5 BOD 26-04 — リスクベースのトリアージを義務化した指令

### BOD 26-04 とは

**BOD（Binding Operational Directive、拘束的運用指令）**は、CISA が米国の連邦政府機関（国防・情報機関などを除く）に出す、従うことが義務付けられた指令です。

2026年6月10日、CISA は **BOD 26-04「Prioritizing Security Updates Based on Risk（リスクに基づくセキュリティ更新の優先順位づけ）」** を出しました。この指令は、次の 2 つの指令を廃止して置き換えるものです。

| 廃止された指令 | 内容 |
|---|---|
| BOD 19-02（2019年） | インターネットに公開されたシステムの Critical の脆弱性は 15 日以内、High は 30 日以内に修正する（**CVSS ベース**） |
| BOD 22-01（2021年） | KEV に載った脆弱性を、原則 2 週間以内に修正する（**KEV ベース**） |

指令の背景では、「攻撃者が AI を使うことで、パッチの公開から悪用までの時間がさらに短くなりうる」と述べられています。そのため、**すべての脆弱性を同じように扱うのではなく、リスクの高いものに対応を集中させ、リスクの低いものは後回しにする**方針がとられました。

### 4 つの判断材料

BOD 26-04 では、次の 4 つの質問への答え（はい／いいえ）の組み合わせで、修正期限が決まります。

| 判断材料 | 質問 | 誰が答えるか |
|---|---|---|
| **公開状態（Publicly Exposed）** | 脆弱な資産は、インターネットなどから信用されていない主体がアクセスできるか | 各機関 |
| **KEV への掲載（In the KEV）** | その CVE は KEV に載っているか | CISA |
| **自動化可能性（Automatable）** | 攻撃の手順をすべて自動化できるか | CISA（Vulnrichment の SSVC） |
| **技術的影響（Technical Impact）** | 攻撃者は資産を完全に制御できるか（total）、部分的か（partial） | CISA（Vulnrichment の SSVC） |

これは、3.4 節の **SSVC の考え方をもとに**、KEV と組み合わせて単純化したものです。注目すべきは、**CVSS のスコアが判断材料に含まれていない**ことです。

### 修正期限の表

|---:|---|---|---|---|---|

| 2 | はい | はい | はい | 部分的 | **3 日** |

| 8 | はい | いいえ | いいえ | 部分的 | 60 日 |
| 9 | いいえ | はい | はい | 完全 | **3 日 ＋ フォレンジックトリアージ** |
| 10 | いいえ | はい | はい | 部分的 | 14 日 |

（出典：CISA, BOD 26-04 Table 1: Remediation Timelines を翻訳）

この表から、次のような特徴が読み取れます。

- **最短は 3 日**。BOD 22-01 の 14 日から大幅に短くなった
- **KEV に載っていなくても 3 日になる場合がある**（5 行目：インターネットに公開されていて、攻撃を自動化でき、完全に乗っ取れる）。「KEV だけ見ていればよい」わけではない
- **「フォレンジックトリアージ」**：KEV に載っていて完全に乗っ取れる脆弱性では、修正するだけでなく、**すでに侵入されていないかの調査**も求められる。修正パッチを当てると痕跡が消えることがあるため、CISA の実装ガイダンスでは、パッチ適用前に証拠を保全するよう求めている
- **リスクの低いものは後回しにしてよい**（15・16 行目）。対応しないのではなく、「急がなくてよい」と明示している

### 期限は状況に応じて変わる

修正期限は固定ではなく、状況に応じて変わります。

- インターネットから切り離す（公開状態を「いいえ」にする）と、期限は延びる。つまり、**すぐにパッチを当てられない場合の正当な緩和策**として認められている
- 後から KEV に追加されると、その時点で期限が短くなる
- 期限は、KEV に追加された日か、各機関が自分の資産でその脆弱性を見つけた日の、**早いほう**から数え始める
- 各機関が公開状態を報告していない資産は、CISA が「ベストエフォート」で判定する。パブリック IP で通信している、資産の種類のタグが「network」である、KEV に載った CVE でそのソフトウェアが一般にインターネットに面するものである、のいずれかに当てはまれば「公開」、どれにも当てはまらなければ「社内」として扱う
- 自動化可能性と技術的影響の情報がない CVE（KEV に載っていないもの）は、CISA などがメタデータを提供するまで、それぞれ「いいえ」「完全」として扱う。KEV に載った CVE には、CISA が必ず Vulnrichment のデータを付ける

### 実際のデータに当てはめると

2025〜2026年に公開された CVE（131,116 件）すべてに、この表を当てはめてみます。「すべての資産がインターネットに公開されている場合」と「すべて社内にある場合」に分けて集計しました。SSVC の情報が付いていない 10,475 件は、上のガイダンスに従い、自動化可能性「いいえ」、技術的影響「完全」として扱っています。

> **集計方法**：「KEV に載っているか」は、KEV カタログ（2026.10.16 版）と CVE ID で突き合わせて判定しました。対象の CVE は **CVE ID の年ではなく公開日**で選んでいるため、CVE-2024-xxxx のような古い ID でも 2025年以降に公開されたものは含まれます。そのため、対象のうち KEV に載っている CVE は 384 件（CVE-2025・2026 の ID が 366 件、それより古い ID が 18 件）です。なお、この範囲では KEV に載っている 384 件と、SSVC の悪用状況が active の 384 件は完全に一致していました。この表は [`scripts/bod2604_simulation.py`](../scripts/bod2604_simulation.py) で再現できます。

| 修正期限 | 公開されている場合 | 社内にある場合 |
|---|---:|---:|
| 3 日 ＋ フォレンジックトリアージ | 330（0.3%） | 157（0.1%） |
| 3 日 | 9,352（7.1%） | 0 |
| 14 日 | 63,743（48.6%） | 227（0.2%） |
| 60 日 | 57,691（44.0%） | 30,088（22.9%） |
| 次回の定期アップグレード時 | 0 | 100,644（76.8%） |

同じ脆弱性でも、**資産がどこに置かれているか**で、求められる対応の速さが大きく変わることが分かります。社内の資産であれば、約 8 割は急がなくてよいと判断されます。

### 適用範囲と導入スケジュール

BOD 26-04 の義務の対象は米国の連邦政府機関だけです。しかし、判断材料はすべて公開されているため、**民間企業や日本の組織でもそのまま参考にできる**モデルになっています。

| 時期 | 求められること |
|---|---|
| 発出と同時（2026年6月10日） | 脆弱性管理の方針を見直す（フェーズ I） |
| 60 日以内 | 脆弱性管理の手順を、新しい方式に合わせて更新する（フェーズ II） |
| 180 日以内（2026年12月ごろ） | 表の修正期限を守る。外部からアクセスできる資産に、公開状態などのタグを付けて管理する（フェーズ III） |

## この章のまとめ

- CVSS 基本スコアは「最悪の場合の深刻度」であり、**リスク**そのものではない。実際に悪用されるのはごく一部の脆弱性である
- **CVSS v4.0 の脅威評価基準**は攻撃の状況をスコアに反映できるが、CNA が値を入れることはほとんどなく、**利用者が埋める**必要がある
- **CISA KEV** は「実際に悪用された脆弱性」のカタログで、最低限対応すべきもののリストとして使える。ただし網羅的ではない
- **SSVC** はスコアではなく「次に何をするか」を決定木で導く手法で、CISA が判断材料の一部を CVE レコードで提供している
- **BOD 26-04** は、公開状態・KEV・自動化可能性・技術的影響の 4 つで修正期限を決める指令で、**CVSS ではなくリスクに基づくトリアージ**を米国の連邦政府機関に義務付けた
- どの仕組みを使うにしても、最終的には「**その脆弱性が自分たちの環境にあるのか、どこにあるのか**」を知っていることが前提になる

次の章では、その第一歩として、NVD の情報を読んで「自分たちの環境が影響を受けるか」を判定する演習を行います。
